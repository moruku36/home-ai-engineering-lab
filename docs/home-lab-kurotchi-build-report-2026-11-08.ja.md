# ホームラボとクロッチの構築レポート

基準日：2026-11-08（JST）
対象：Intel NUC のホームラボ、Mac mini、OpenClaw（クロッチ）、開発用 CLI とラウンジ連携

**English summary:** The lab progressed from a Compose-based automation and observability host to a second Mac mini host with OpenClaw, limited CLI generation, a dedicated GitHub test, and scheduled status exchange. The latest receive-side check confirmed that one message and its provenance were available in the normal conversation. General GitHub operations still encounter an approval-registration failure. Historical checks, recent observations and pending acceptance are distinguished below; this report does not certify current fleet health or fully autonomous operation.

## 1. ここまでにできたこと

最初の成果は、サービスを起動することだった。その後は、収集した情報をレポートにする、監視する、バックアップから戻せるか確かめる、別ホストの AI に仕事を依頼する、仕事の状態を共有する、という順に対象が広がった。

11月8日時点では、次の実績がある。

- NUC で Docker Compose の自動化・監視基盤を構築し、GitHub 情報の収集から Markdown レポート生成、MCP 経由の参照までを手動実行で確認した。
- Prometheus・Grafana・node_exporter を起動し、収集先の正常応答と API 経由の問い合わせを確認した。kind の2ノード構成も過去の限定試験で起動・Ready を確認した。
- ローカル暗号化バックアップと隔離した復元試験を実施し、意図的に停止したサービスをバックアップ処理が勝手に起動する問題を修正した。
- 仮想 NIC を持たない解析 VM を用意し、Workbench の基本的な MCP 通信と REA／Ghidra の限定出力を確認した。解析能力の正式受入れは残している。
- Mac mini に OpenClaw を導入した。クロッチから Codex と Claude Code の起動に加え、Codex による公開情報を基にした編集計画の生成、Claude Code の短い応答を確認した。
- 専用の GitHub 試験では push・PR 作成・マージまで成立した。一方、通常の作業では別の承認登録エラーが残った。
- ラウンジの定期処理による状態投稿と、通常会話から受信本文・出典を読む経路を確認した。受信した指示は自動実行しない。

いずれも確認した対象・時点・経路に限った成果である。全サービスの現在の健全性、任意のリポジトリに対する自動開発、三者の完全自動往復、長期の無人運用は、まとめて合格とはしていない。

## 4. NUC 側で困ったことと対処

### 4.1 バックアップが停止中のサービスを起動してしまう

旧処理は全スタックを止めてから全スタックを戻す作りだった。このため、意図的に停止した Open WebUI まで夜間処理で再起動する問題があった。

処理前に動いていたスタックを把握し、その集合だけを停止・再開する方式に修正した。停止中のサービスのデータはバックアップ対象に残した。スタブによる論理確認と実機の実行で、Open WebUI が停止したままであることを確認した。

得られた教訓は、バックアップの成功条件に「ファイルを作れた」だけでなく「運用上の停止状態を保存できた」を含めることだった。[S1][S3]

なお、10月のローカル復元試験の成功は、後日の別バックアップの復元成功を意味しない。10月28〜29日の構成確認では暗号化バックアップと保存済みチェックサムの一致は記録されたが、その復元試行は完了していない。NUC 外への保管や observability ボリュームの保護も、従来資料では未整備のままである。[S2][S3]

### 4.2 API 枠を使い切ると、再実行のほうが悪い結果になる

GitHub の無認証 API 予算には上限がある。同じ日に再収集したところ、先に作った詳しいレポートを、取得範囲の狭い結果で上書きしてしまった。

最初の保護ロジックは保存済みフィールドに依存していたため、旧形式のスナップショットには効かなかった。そこで毎回内容から完全性を計算する方式へ変え、旧形式の試験を追加し、実機へ反映した。

当時の手動実行では109リポジトリを対象とした収集が成功したが、最新コミットなどには未取得が残り、レポートは `PARTIAL DATA` とされた。この数字は当時の一回の観測であり、現在の対象数や網羅率ではない。定期実行の設定済み、手動実行の成功、必要項目を全部収集できた、の三つを分けたことが重要だった。[S1]

### 4.3 イメージ名の指定とバージョン整合性

Grafana の初回起動は、指定した省略タグが存在せず失敗した。公開されている完全なバージョンへ固定して対処した。これは上流サービスの不具合ではなく、ラボ側の定義の問題だった。

kind では、取得した最新 kubectl とクラスタのバージョン差がサポート範囲を外れた。kubectl とノードイメージを固定し、チェックサム／digest の確認を組み合わせた。また、クラスタ作成の待機だけでは worker の Ready を待ち切れなかったため、全ノードの Ready 待機を明示した。再作成と二回目の実行で限定的な動作を確認した。[S1]

### 4.4 公開 Compose と実際の構成が一致しない

Grafana の更新候補は、実環境の Compose 識別チェックで `changed=0` のまま停止した。外部の override ファイルにネットワークや他サービスの定義があり、想定した入力と異なっていたためである。

対処では外部ファイルを消したり並べ替えたりせず、順序と既知のハッシュを保全したうえで、Grafana イメージ以外の実効差分を拒否するようにした。所有者から適用成功・`changed=2` の報告があり、API でも更新後のバージョンと database ok を確認した。

n8n でもリポジトリのタグと実機側のイメージ参照に差があった。自作 jobs／MCP はソースと実行中イメージの対応が未確定だった。「公開 main が新しいから、実機も同じ」と考えず、実際の入力・イメージ・ローカル差分を確認してから更新する必要があった。[S2]

### 4.5 監視の入口が見えることと、必要な情報が揃うこと

Grafana の health やログイン成功、Prometheus の `up=1` は、それぞれ有用な証拠である。ただし、それだけでは欲しいパネルに最新データが表示されることも、家庭全体の通信量が収集できることも証明しない。

既存 node_exporter の系列と、計画中のホスト NIC 用 snapshot、DNS 試験、統合ダッシュボードを区別した。Kuma についても、異常を検知できることと、通知先に届くことを分けた。通知チャネルや Push の設定が未完了なら、配送まで完成したとは書かない。[S1][S2]

### 4.6 解析ツールの終了コード0を、解析能力の合格にしない

隔離解析 VM では Workbench の initialize、tools/list、ping、doctor、正常終了を確認した。ただし列挙された16ツールすべてを実行したわけではない。

REA／Ghidra は自作の無害な ELF に対して JSON を返し、終了コードも0だった。しかしファイルの mtime 変化、評価条件との差、独立した実行由来の未確認が残り、元の `FAIL` と `REPORT=UNVERIFIED` を維持した。基本的な VM 操作の条件付き受入れと、解析能力の受入れを分けた。この慎重な判定は、成果を否定するためでなく、どこから次の試験を始めるかを明確にするためである。[S4]

## 5. Mac mini とクロッチで困ったことと対処

### 5.1 リモート接続と無人運用は別の課題だった

初期構築では、SSH エージェントが多数の鍵を提示して認証失敗回数に達する問題と、キーボード配列差による入力の不一致が起きた。認証方式を切り分けて接続し、tailnet 経由の対話シェルまで確認した。

一方、画面ロック、再起動後の復帰、スリープ、FileVault、公開鍵ログイン、最終的な有線化・監視登録は別の確認項目である。11月8日の作業でもログイン後の画面ロックが操作の障害になった。SSH で入れることを、GUI を解除できることや、完全なヘッドレス運用の証明と混同しなかった。[S5][O4]

### 5.2 OpenClaw 本体、作業環境、ブラウザを分けて考える

OpenClaw 本体は Mac mini に導入されていても、クロッチの作業用エージェントは Docker 内に隔離されていた。この状態では、Mac にある CLI やその認証領域が、そのままエージェントから使えるとは限らなかった。

11月7日には、対象の作業用エージェントを Mac 直接実行へ切り替え、Gateway の正常とホスト側コマンドの限定実行を確認した。これは作業環境のアクセス範囲を広げる変更なので、全体の隔離を一括で無効化する話と分け、確認のうえで対象を限定した。

また、専用ブラウザの Docker ネットワーク・ループバック公開・Docker socket 未マウントという11月6日の構成記録は、作業用エージェントの実行先とは別の層である。「Docker を外した」という一言では何の境界を変えたか伝わらない。作業実行、ブラウザ、認証を別々に記録する必要があった。[S6][O1]

### 5.3 CLI はインストール、起動、生成、成果物の順に確認した

最初は Mac 側の Codex CLI／Claude Code CLI の導入とログインまでだった。11月7日にクロッチから両 CLI のヘルプ表示を確認し、その後、Codex は公開リポジトリの読取り・Web 検索を伴う日本語の編集計画を生成し、Claude Code は短い応答を返した。

Codex の計画には件数の誤記があり、生成できたことと正しい成果物が完成したことを分けた。別作業ではローカルの変更を確認したが、編集の最終確定と公開は未完了として報告されていた。したがって、今回の到達点は「クロッチ経由で限定的な生成ができる」であり、「任意の開発を正しく完了し公開できる」ではない。[O1]

### 5.4 GitHub の専用試験成功と、通常作業の承認エラーが同時に存在した

専用の接続試験では、ブランチ作成・ローカルコミット・push・PR 作成を経て、[テスト PR #1](https://github.com/moruku36/kurotchi-connection-test/pull/1) のマージを GitHub 側で確認した。本書作成時にも PR が closed／merged であることを読み戻した。

ところがクロッチ側の結果記録は成功を確定できず停止していた。ここではマージを再実行せず、外部の状態を照合し、試験用のゲートと許可を閉じた。外部の変更が成功していても、結果の回収に失敗すると、エージェントからは「不明」に見える。これを単純な再試行で解決しないことが重要だった。[O2]

その後の通常作業では、GitHub CLI のログインが使えることや限定的な dry-run の成功が確認された一方、子セッションの承認登録で `operator.approvals` 不足が報告された。Git コマンドが実行される前に止まっているため、GitHub の認証失敗や対象リポジトリの権限不足と断定できない。

管理画面の別接続に権限があることも、失敗した子セッションに同じ権限がある証拠にはならない。診断情報の読み取りにも制約があり、どの接続元に何が不足しているかは未確定のままである。[O3]

公開されている [OpenClaw v2026.11.1 の承認 API 定義](https://github.com/openclaw/openclaw/blob/v2026.11.1/src/gateway/methods/core-descriptors.ts#L48-L52)でも、承認操作には `operator.approvals` が必要とされる。この上流資料はエラーの段階を理解する参考であり、ラボの現在のバージョン・対象接続の実効 scope・直接原因を確定する証拠ではない。過去の類似不具合と今回の障害が同一かも未確定である。

**基準日時点でこの問題は未解決。** 対処の順序は、許可された監査情報で失敗した接続と承認登録段階を特定し、原因が分かった場合にだけ対象を絞った修正を検討すること。拒否された診断を別経路で読む、権限をまとめて増やす、GitHub の再ログインで直ったと推測する、といった対応は解決実績に含めない。

### 5.5 ラウンジは「投稿」「定期読取り」「通常会話での利用」が別々だった

定期ジョブが受信箱を読めても、その内容がクロッチの通常会話から見えるとは限らなかった。また、既存の定期処理は成功していても、別途試した新しい読取り経路は停止することがあった。既存の仕組みを確認せず新しいジョブを増やすと、重複や許可範囲の混乱につながる。

11月8日朝の記録では、状態変化に応じた自動投稿が二つの宛先に届き、GitHub 上で内容を読み戻した。さらに、既存の定期読取りで取得した受信本文と出典を、通常会話から読める専用ファイルへ保存する経路を整えた。実際の連絡1件で本文と出典の一致を確認した。[O5]

この受信データは未信頼の情報として扱う。そこに依頼が書かれていても、そのまま操作権限にはしない。リンク先の自動取得や外部転送も、この受信成功から自動的に許可された扱いにはしない。

定期投稿には稼働時間帯・間隔・送信上限・情報鮮度の制限を設け、状態が古い場合は投稿を止める設計とした。確認できた自動投稿と1件の受信利用は大きな進展だが、全周期・再起動後・重複・遅延・相手不在を含めた三者往復の受入れは残る。

## 7. 次に進める順序と合格条件

1. **承認登録エラーを切り分ける。** 失敗した接続・処理段階・不足権限を、許可された情報だけで特定する。一般化した原因と修正範囲を残し、必要な変更は別途確認する。
2. **既存の仕事を一つ完了させる。** 並行中の作業を保全したまま、入力、変更、最小限の検証、公開許可、公開結果の読み戻しまでを同じタスクで確認する。
3. **ラウンジの継続性を確認する。** 投稿の存在だけでなく、同じ情報を受信者が読めること、鮮度と重複の扱い、失敗時にどう停止・報告するかを確認する。
4. **サービス単位で運用を引き継ぐ。** 正常基準、意図的な停止、未完了の通知、復旧手順、変更できる範囲を対象ごとに照合する。
5. **記録を更新する。** 成功した時点と対象を追記し、失敗・未確認を消して成功に見せない。過去資料を歴史として残し、最新の判断がどれか分かるようにする。

これは次段階の提案と受入れ基準であり、記載した操作を今回追加実行したという意味ではない。

## 8. 記事化するときの要点

記事の中心にできるのは、「サービスを起動するホームラボ」から「仕事と状態を受け渡せるホームラボ」へ進んだ経験である。具体例として、停止状態を守るバックアップ、不完全な結果で上書きしない収集、Compose 差分の保全、CLI の段階試験、結果不明時の照合、受信情報と実行許可の分離がある。

使える表現：
