# Brotli 脆弱性対応と n8n 更新の記録（2026-10-25）

## 結果と対象範囲

CVE-2026-111497 への対応として、n8n を **2.43.5 から 2.44.6** に更新した。
2026-10-25 に所有者端末の `updated_verified` 結果を確認し、その後、所有者が SSH トンネル経由で n8n の画面表示を確認した。

これは予防的な更新の記録であり、侵害があったという証拠は得ていない。
実ワークフローの実行、全 Python 環境、コンテナイメージの attestation は未検証。
今回の n8n 更新対応はこの範囲で完了とした。

この文書は実施記録であり、任意の環境にそのまま適用できる更新スクリプトではない。
実機の設定・データと、リポジトリに保存された構成例は区別する。
文書公開によって構成例や別の実装ブランチが実機と同期したことにはならない。

## 1. 更新前後に確認した値

| 対象 | 更新前／調査時 | 更新後／判断 |
|---|---|---|
| n8n | 2.43.5 | 2.44.6 |
| n8n コンテナ内 Node.js | 26.7.0 | 26.12.1 |
| Node.js が報告する Brotli | 1.2.0 | 1.2.0（公式修正の取り込みを別途確認） |
| 候補の Brotli リンク方式 | 初期調査では未確認 | `node_shared_brotli=false`、ロード済み Brotli 共有ライブラリなし |
| 調査対象の Python コンテナ 2 個 | Python 3.12.15。配布メタデータに Brotli／brotlicffi なし | その 2 環境へのパッケージ追加・更新は不要 |

Python の確認は指定した 2 コンテナの distribution メタデータに限る。
ホスト、別の仮想環境、他の依存関係や同梱コードまで検査済みという意味ではない。
ホスト側 Node.js の版を、n8n コンテナ内の版の代わりには使わなかった。

## 2. 公式情報と更新候補の判断

Google Brotli の [v1.2.1 リリース](https://github.com/google/brotli/releases/tag/v1.2.1) は、CVE-2026-111497 の修正を記載している。

Node.js の [2026 年 10 月セキュリティ告知](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)と
[v26.12.1 リリース](https://nodejs.org/en/blog/release/v26.12.1)を照合した。
後者はこの CVE に対する Brotli 修正の cherry-pick を明記し、[対応コミット](https://github.com/nodejs/node/commit/a6040b50d9)も公開されている。

一方、同タグの [Brotli version.h](https://raw.githubusercontent.com/nodejs/node/v26.12.1/deps/brotli/c/common/version.h) は 1.2.0 のままだった。
したがって、Brotli の表示番号が 1.2.0 という理由だけで「未修正」と判断するのは誤りだった。

n8n は [2.44.6 の公式リリース](https://github.com/n8n-io/n8n/releases/tag/n8n%402.44.6)と
[同タグの Dockerfile](https://github.com/n8n-io/n8n/blob/n8n%402.44.6/docker/images/n8n/Dockerfile)を確認した。
公式配布イメージの取得後、digest・source・version を照合し、候補をネットワークなし・データ接続なしの隔離コンテナで検査した。
実測 Node.js 26.12.1 と内蔵 Brotli の組合せは、公式バックポートの説明と整合した。
更新にはタグの再解決ではなく、確認した固定イメージを使った。attestation の検証まで行ったとは扱っていない。

## 3. 途中で止まった検査と修正

### Brotli の表示番号だけを比較した判定

最初の候補検査では Brotli 1.2.1 という表示を要求して停止した。
この時点では稼働中 n8n を変更していない。
公式 Node.js の修正取り込み、据え置きの版定義、候補のリンク方式を照合して判定を訂正した。
修正有無は、表示文字列だけでなく、配布元・修正コミット・実ランタイムの組合せで判断する。

### Docker image inspect の省略可能フィールド

続く更新手順は、候補イメージの `Config.Volumes` を Go template で直接参照した際に失敗した。
読み取り診断でテンプレートエラーを特定し、旧イメージの n8n が稼働中で、更新の実行記録も未作成と確認した。
この失敗から復元操作や旧版の再起動は行っていない。

[Docker の公式互換性情報](https://docs.docker.com/engine/deprecated/#emptynil-fields-in-image-config-from-inspect-api)では、
空または nil の image Config フィールドが API 応答から省略される場合がある。
任意フィールドを `index` で取得するよう修正し、Volumes は null／空 map のみ許可した。
非空の volume 宣言や不正な型は拒否し、固定イメージ・digest・source・version の照合は維持した。
失敗時には秘密の出力やコマンド全文を表示せず、固定の step 名を返すようにした。

新版は Python の合成回帰試験 29 件と Go template の合成 4 ケースで検証した。
その後、所有者端末の候補メタデータ読取り検査が成功してから更新へ進んだ。
合成試験は実機更新の成功証拠とは別に扱った。

## 4. 実施した更新の順序

1. **停止前の確認**  
   既存 Compose、永続データの範囲、他の利用コンテナの有無、空き容量、旧イメージの保持を確認した。
   候補の固定イメージと実ランタイムを検査し、既存の暗号化・復号手段で非秘密データの往復を確認した。
   この段階は実データのバックアップ完了を意味しない。
2. **n8n のみ停止して整合性を確保**  
   他サービスを停止せず、停止後の永続データと元の構成・必要な設定を保全した。
3. **暗号化バックアップと読戻し**  
   暗号化バックアップを別の非公開作業領域へ復号し、データ・メタデータ・設定の一致を検証した。
   オフラインコピーの SQLite integrity と、ワークフロー・資格情報・ユーザーの保存件数を確認した。
   本文や資格情報値は表示していない。
4. **固定イメージへ切替**  
   Compose の n8n イメージ指定だけを変更し、n8n のみ再作成した。
   マイグレーションが起こり得る開始点を記録した。
5. **更新後の受入れ**  
   `/healthz` と `/healthz/readiness` の両方が HTTP 200 であること、
   起動イメージが検査済み候補と同一であること、保存オブジェクト数と既存実行設定が維持されたことを確認した。
   他コンテナの保持と設定の不変も検証し、`updated_verified` を確認した。
   続いて所有者がトンネル経由の画面表示を確認した。

停止時間は、整合性バックアップ・読戻し・起動後検査を含む。所要時間の保証や性能測定はしていない。
この更新では新しい認証、権限・ネットワーク設定、定期ジョブの追加は行っていない。

## 5. 失敗時の扱いと復旧可能性

- 旧イメージ、暗号化済みの更新前バックアップ、実行記録を保持した。
- 停止後に失敗しても旧版を無条件に自動起動しない。処理の停止表示だけでコンテナの停止状態は断定しない。
- 新版を一度でも起動した後は、DB が移行済みの可能性がある。イメージだけを旧版へ戻す操作は安全な復旧とは扱わない。
- 復旧が必要なら、失敗時のデータを保全し、検証済みの更新前データと元の構成を整合した組で復元してから旧版を起動する。
- 今回はバックアップの復号・内容照合と SQLite 整合性を確認したが、本番データを旧状態へ戻す復旧演習は行っていない。

一般の保全方針は [バックアップ・復元](backup-restore.md)、通常の運用は [運用手順書](ops-runbook.md)を参照。
既存の全体バックアップ手順と、今回の n8n 限定更新の検証範囲は同一ではない。

**教訓:** 版文字列だけでバックポートを見落とさず、省略可能な API フィールドを安全に扱う。
更新の成否は、候補検証・バックアップの読戻し・更新後ヘルス・保存データ・画面・実ワークフローを分けて記録する。
