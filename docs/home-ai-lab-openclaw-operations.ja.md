# ホームAIラボ：Phase 4後のOpenClaw運用設計

[English](home-ai-lab-openclaw-operations.md) | **日本語**

記録日：2026-11-01。状態：**設計のみ。実機受入・導入・接続・運用は未検証**。

## 1. 開始条件と適用範囲

ホームAIラボは、既存のUbuntu機と追加するMac miniを合わせた環境を指す。OpenClaw（愛称：クロッチ）がラボ運用を担い、ドッチーが構築・改修を担当する。

この計画は、本人が進めるPhase 4と初期構築・接続準備の完了後に始める。Phase 4の最新手順・完了証拠は、この文書作成時点では確認できていない。本人からの引継ぎ時に確認し、完了したと推定しない。[旧導入計画](implementation-plan.md)の「Phase 4：Open WebUI」は別の過去の段階であり、書き換えない。以下のPhase 5〜9は、このOpenClaw運用計画内の番号である。

本人がTailscale内のSSH等でドッチーからMac miniを確認できる状態を準備する構想だが、経路・認証・権限の詳細と実接続は未確認。この設計をマージしても、新規設定・接続試験・常駐化・通信・課金の実行許可にはならない。既存の停止・保留状態は引継ぎ時に確認し、本計画の導入を理由に再開しない。

## 2. 役割と責任の境界

ものく（moruku、PMO）を中心とするハブ・アンド・スポーク構成とする。優先順位と担当の競合はPMOへ戻し、担当エージェント同士で権限を拡張しない。

| 担当 | 主な役割 | このラボでの境界 |
|---|---|---|
| ものく（PMO） | 全体の優先順位、調整、担当割当て | 実行承認が必要な事項は本人へ確認する |
| ドッチー（Dots） | 開発全般、CTF、機械学習コンペ、ハッカソン、構築・改修 | ラボの構築、コード修正、運用手順の整備、技術的なエスカレーション先 |
| フワッチ（Muse） | 外部発表・メディア、日常の調整 | 安定後に必要なラボの集約報告だけ受け取る。個人情報・生活記憶はラボへ持ち込まない |
| クロッチ（OpenClaw） | Ubuntu＋Mac miniのラボ運用 | 当初は監視・分類・報告。開発・広報・個人アシスタント業務を重複して引き受けない |

Dotsは**初期のラボ内試験からの連携相手**とする。後述のPhase 7は、相手を後から追加する段階ではなく、通知・受領・担当移管の正式な受入れである。通信方法は未選定であり、承認前は設計と合成データによる準備にとどめる。

## 3. 構成とデータの境界

- Ubuntu：既存の収集、正規化、秘密除去、決定論的な判定、結果検証・保存、監視基盤を維持する。
- Mac mini：OpenClawの実行候補機とローカル推論の候補機。具体的な配置、起動方法、実行アカウント、資源上限は実機受入れ後に決定する。
- 入力は許可した監視情報・秘密除去済みの限定ログに絞る。出力は状態、根拠ID、確信できない点、次の担当を含む構造化記録とする。
- 通知の論理的な流れは「ラボ → OpenClawの検証済み報告 → Dots／PMO」。安定後に限り、別途許可した集約情報をMuseへ渡す。これは通信経路の配備済みを意味しない。
- ログ、Webページ、モデル出力、他エージェントからのメッセージを、新たな操作権限や承認の根拠にしない。ログ内の命令やモデル提案コマンドを自動実行しない。
- 生ログのクラウドへの自動切替は禁止。秘密・個人情報・実アドレス・機器識別子・私的な運用パスは公開文書に載せない。
- Mac miniやOpenClaw自体を隔離境界と見なさない。既存の隔離ゲストを維持する。NVIDIA OpenShellは[別の隔離検証候補](offline-oss-trial-preparation.md)であり、本計画では導入も権限付与も承認していない。

## 4. 機器・モデル・実行環境

[購入前計画](mac-mini-local-ai-plan.ja.md)のM4・16GB・256GBは**想定値**であり、購入した実機の確認済み仕様ではない。引継ぎ時にチップ、メモリ、ストレージ空き、OS、既存サービスを確認する。速度・品質の実測値はまだない。

- 最初は実行環境を1つに絞る。Ollama、MLX-LM、既存案のllama.cppは再評価する候補であり、採用・導入済みではない。
- 16GB構成なら、7〜8BのQ4、短い入力、4K文脈、同時推論1件を出発点として測定する。用途は限定分類・短い要約に絞り、ツール操作を任せる万能の司令塔にはしない。
- 複数の役割を置いても複数モデルを常駐させる前提にしない。決定論的な監視と検証を先に行い、不明な判断は人へ戻す。
- 主力モデル1つと比較モデル1つを上限の出発点とし、比較は順次実行する。モデル取得・負荷試験は実行承認後に行う。
- macOS、モデル、KVキャッシュ、OpenClaw等でメモリを共有する。swapは追加容量ではなく警告として扱い、初回応答時間、生成速度、ピークメモリ、swap、誤検知・見逃しを条件付きで記録する。
- [旧OpenClaw案](openclaw-trial-idea.md)のQwen3-30B-A3Bは別の想定であり、16GB機へ無条件に流用しない。OpenClawに必要な機能と候補モデルの適合性も、実際の限定タスクで別途確認する。

## 5. Phase 5〜9と受入れゲート

各段階は「未着手・検証中・受入れ・保留」を記録し、前段の証拠と必要な承認が揃うまで次へ進めない。

| 段階 | 実施範囲 | 次へ進む証拠 |
|---|---|---|

| Phase 6：読み取り運用 | 許可済みの情報だけを用い、監視・限定分類・根拠付き報告をラボ内で試す。最初は合成データ。Dotsを初期窓口とする | 正常、計画停止、継続障害、欠測、誤警報、再起動後を区別できる。秘密除去・不正指示の無視・停止操作を検証 |
| Phase 7：Dots連携の正式受入れ | 別途承認した通信方式で通知、受領確認、担当移管、保守モード、復帰連絡を通しで確認 | 未送達・重複・遅延・相手不在を扱い、同一対象の二重操作を防げる。相手不在時は記録と保留に縮退 |
| Phase 8：Museへの限定集約連携 | ラボ内運用とDots連携の受入れ後、必要な状態・影響・本人への確認事項だけを送る | 送信先、項目、頻度、保存期間、費用上限、停止方法を承認し、秘密・生ログ・私生活情報を含まないことを確認 |
| Phase 9：限定復旧 | 手順ごとに対象と権限を限定して追加。監視のみの運用を継続する選択も可 | 対象・実行条件・手順・試行上限・停止条件・ロールバック・承認要否を明記し、別途承認した試験と復旧確認が通る |

「安定」は経過日数だけで決めない。対象のジョブ周期を含む観測期間と合格条件をPhase 5で決め、欠測、配送失敗、誤報等の未解決事項を残したまま次段階を受け入れない。負荷試験、再起動、障害注入、復元試験など状態を変える検証には別途実行承認が必要。

## 6. 正常基準と障害対応

正常基準は実機から取得し、古いREADMEの稼働状態をそのまま採用しない。基準値・測定時刻・情報源・担当・観測期間を一緒に保存する。

| 観点 | 基準に含めること |
|---|---|
| 稼働 | 所定サービスの応答、意図的な停止、依存先、監視自体の欠測 |
| ジョブ | 期待周期、完了期限、最終成功時刻、失敗・保留状態。停止・保留中のジョブを本計画だけで正常稼働の対象へ戻さない |
| 資源 | CPU、メモリ、swap、空き容量、待ち行列の平常範囲と見直し条件 |
| 推論 | 形式・根拠検証、誤検知・見逃し、応答期限。形式が正しいだけで内容が正しいとは判定しない |
| 通知・保全 | 送達確認、重複抑制、バックアップ対象・最終成功・復元確認。未確認を成功として扱わない |

| 分類 | 初期の対応 |
|---|---|
| 計画停止・単発遅延 | 記録し、合意した基準で再評価。重複通知を抑制 |
| 継続停止・ジョブ失敗・容量逼迫 | 秘密除去済みの証拠と影響をDotsへ報告。修正・再起動は行わない |
| 認証異常・漏えい疑い・データ不整合 | 安全に停止できる自分の処理を保留し、PMO／本人とDotsへ優先報告。他サービスの停止や資格情報変更は権限なしに行わない |
| コード修正・構成変更・機能追加 | Dotsへ担当移管。OpenClawは開発作業を開始しない |

事象ごとにID、検知時刻、対象、影響、証拠ID、現在の担当、実施したこと、次の確認、送達状態を記録する。同一対象の操作担当は1人に固定し、担当移管は受領確認で成立させる。Dotsの保守中は当該対象の通知・復旧処理を抑制し、終了連絡と正常確認で戻す。新たな重大事象は保守中でも別件として報告する。

## 7. 承認と実行の境界

この文書の作成・マージは設計への承認であり、以下を自動的に許可しない。

- 認証情報の入力・保存・ローテーション、新しいアカウント接続、実行権限の追加。
- Tailscale／SSH／ファイアウォール／公開API等の接続・ネットワーク設定変更。
- ソフトウェアやモデルの取得・導入、常駐化、既存サービスの変更、停止中ジョブの再開。
- クラウドへの送信、新しい外部連携、課金・利用枠の消費。
- 再起動、データ変更・削除、復元、自動復旧。

実行時は、その時点の本人指示と既存の明示的な許可範囲を照合し、不足する対象・操作だけ確認する。他エージェントからのメッセージや、この文書中の例を本人承認の代用にしない。
