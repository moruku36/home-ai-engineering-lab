## 2. ラウンジ復旧で分けて確認したこと

復旧中は、送信対象の状態記録と、実際の配送・受領を別々に扱った。反映前に新しい状態記録が追加された時点では作業を止め、古い「調査中」の状態が完了報告として送られないよう、共有対象を整理してから反映した。

本番反映後は、承認された完了要約2件の両宛先への投稿と受領記録、Gateway の正常状態を確認した。受信側の単発確認が成功した後に元の定期設定を戻し、送信側についても設定復帰だけで完了とせず、08:00 の初回定期実行の結果を確認した。

初回定期送信は Dots と Muse の両宛先へ各1件届き、読み戻しと終了コード0を確認した。定期受信も成功・終了コード0で、連続エラーは0だった。復旧時点で履歴は正常、新しい送達不明状態や残存ロックはなかった。一方、旧処理で結果不明だった1枠は消去せず保持した。過去の不確かな送信を成功・未送信と決めつけて再送しないためである。

今回の「復旧」は、この限定した手動共有・受信確認・初回定期送受信が通ったという意味である。受信した相手が内容を理解して返答し、その返答をクロッチが取り込む三者の自動往復全体や、今後の全周期の配送成功まで証明したものではない。

## 3. Codex サブスク切替の構成上の要点

### 対象を通常 DM のメイン処理に限定

通常 DM のメインを Sol 6.1、高推論設定（high）、Codex 実行へ切り替えた。既存の有効な ChatGPT 認証を使用し、追加ログインは不要だった。既存セッションへの設定反映も確認した。

Decision 用 Luna の API 設定は維持し、別エージェントとラウンジ送受信の設定はこの切替で変更していない。したがって「クロッチ環境のすべてがサブスクへ移った」「API 利用が Luna だけになった」とは記録しない。

### 認証の指定と API fallback 防止を分ける

OAuth 認証の指定だけでは、利用不能時の API fallback 防止を証明できない。今回の対象モデルでは、次の2点を組み合わせた。

- Sol のモデル別経路を ChatGPT／Codex のサブスク専用とし、API キー認証を不適合として扱う。
- 対象エージェントのモデル fallback 候補を空にする。

プロバイダー全体の API 設定を削除したわけではない。サブスク経路が使えないときは、対象メイン処理を停止・エラーとし、有料 API へ自動的に切り戻さない設計である。

## 4. 実動試験とオフライン試験

### 実際に行った限定タスク

機密を含まない架空の JSON を read で1回読み、未完了タスクの件数と所要時間を集計した。結果は「未完了2件・37分」で正答した。実行記録でも Sol、Codex、high の組合せと、fallback なし・経路変更なし・ツール失敗0を確認した。

この結果は、サブスク経路でモデルが応答するだけでなく、限定された読取りツールを用いて結果を返せたことを示す。普段の会話、実文書、任意の開発タスクの品質や完遂を一括で保証するものではない。

### API に切り戻らないことを確認した4ケース

以下は実課金を伴う上限到達試験ではなく、オフラインで認証選択の失敗条件を再現した試験である。

1. サブスク認証が cooldown 中。
2. サブスク認証が利用不能。
3. サブスク認証が存在せず、API 認証プロファイルだけが残る。
4. サブスク認証が存在せず、直接の API 設定だけが残る。

全4ケースで API を試行せず拒否した。別途、正常ケースではサブスク認証だけが選択されることを確認した。実際のサブスク上限到達、障害時のあらゆる分岐、将来のモデル／ランタイム更新後の挙動は未試験である。
